Reviewed production and test source at `8a9991e47ed8e897c3547bbf69fdf0fbeba6088f`,
the existing uncommitted PLAN draft, manifests, inventory, research decisions,
oracle tools, CI and packaging. No production changes were made. This is evidence
for [PLAN.md](../PLAN.md), not a second execution queue. Earlier observations are
identified separately from checks performed during this review.

## Assessment

The library has substantial reusable foundations: bounded parsing and rendering,
six output APIs, explicit font acquisition, managed PNG handling, typed curve and
stroke kernels, retained browser references, and working package isolation.
The current Windows build is healthy. General corporate-logo exactness is not
demonstrated. The main constraint is shared geometry/raster architecture, with
several smaller semantic defects that can be fixed before that transition.

The blocked handoff overstates how much has been settled. Neither historical
activity in a file nor a missing release coverage target prevents the next
implementation slice. Some recent research conclusions also need narrower claims.

## R40: calibration source pin and over-broad quantization proposal

The actual Chrome **153.0.8010.52 release tag** pins Skia
`f8b66b7597c4cc859d3ed190e9c6872241e6721c`. This was freshly verified from the
[release-tag DEPS](https://raw.githubusercontent.com/chromium/chromium/153.0.8010.52/DEPS).
Recent research instead followed Chromium main at the branch-position revision
and used `8b8c3872fbc03f025855db96ce683f34ec98a815`; that is the current optional
`external/skia` checkout. Main/branch position does not supersede a release tag.
The original source-pin section of RASTERIZATION_DESIGN.md was correct; the later
claimed correction and inventory batch 109 are not the matched release pin.

Reading the matched release's
[SkScan_AAAPath.cpp](https://raw.githubusercontent.com/google/skia/f8b66b7597c4cc859d3ed190e9c6872241e6721c/src/core/SkScan_AAAPath.cpp)
confirms that `trapezoid_to_alpha` shifts fixed area right by eight. However,
`fixed_to_alpha` calls a rounded partial-alpha operation with 255, and other
partial-alpha paths multiply then shift. The file itself uses several rules.
This supports investigation of the observed opaque 0.75-coverage error; it does
not prove a universal `floor(256 * coverage)` compositor.

In Lokad.Svg, `SvgConverter.WithCoverage`, `MultiplyAlpha`, `BlendSourceOver` and
`ComposeFractionalChannel` perform different operations. The three copies of
`MultiplyAlpha` combine already quantized byte opacities. Changing their rounding
can change a fully covered pixel: round(128 * 129 / 255) is 65, while truncation
gives 64. Thus integer-edge invariance cannot justify changing all six sites.
The exact fixture set includes 21 alpha/transparency/source-over-tagged entries
and two fractional-coordinate-tagged entries; it is not just opaque integer
rectangles. The design record also retains exact translucent quarter-edge results.

The work order must separate geometric coverage, coverage-mask quantization,
paint alpha, premultiplication, composition and unpremultiplication. Change only
the operation supported by discriminating vectors; preserve exact controls.
Compare every changed candidate to unchanged oracle references. Do not bulk
regenerate mismatch expectations to make a proposed formula pass.

## S12: the miter defect is concrete, conic support is not already present

`SvgStrokeOutline.EmitJoin` computes
`|n1 + n2| / (2 * (1 + dot))`, then compares it to the full miter limit. Its
emitted miter displacement is `halfWidth * (n1 + n2) / (1 + dot)`. Consequently
the tested ratio is half the displacement-to-half-width ratio. Normalize that
ratio consistently before comparison; “half-limit” is an algebraic workaround,
not a new SVG rule.

The matched release's
[SkStrokerPriv.cpp](https://raw.githubusercontent.com/google/skia/f8b66b7597c4cc859d3ed190e9c6872241e6721c/src/core/SkStrokerPriv.cpp)
compares the inverse miter limit against `sqrt((1 + dot) / 2)`. The existing acute
limit-1/default/limit-10 research cases provide branch witnesses. A right-angle
rectangle cannot establish correctness at an acute fallback threshold. Preserve
the diagonal residual separately from fixing the opaque spike.

That same source confirms conic round caps/joins. The current
`SvgCurveFlatten` implements polynomial quadratic and cubic subdivision only;
it has no weighted-conic entry point. “Emit conics into the existing flattener”
therefore needs an explicit bounded representation/conversion implementation.
Preserve authored corners versus curve subdivision vertices, since the retained
rounded-rectangle witnesses show join styles firing at artificial joints.
Neither source observation alone proves Chrome's complete runtime raster route.

## R34: stroke contour overlap still over-accumulates coverage

Two fresh 16x16 opaque-black path probes use stroke-width 2 and fill="none":

```xml
<svg xmlns="http://www.w3.org/2000/svg" width="16" height="16">
  <path d="M2 2L14 14" fill="none" stroke="black" stroke-width="2"/>
</svg>
```

The second input changes only `d` to `M2 2L14 14M2 2L14 14`.

| Comparison | Changed pixels | Maximum alpha/channel error |
| --- | --- | --- |
| Single stroke versus its Chrome reference | 50 | 8 |
| Duplicate subpaths versus their Chrome reference | 50 | 108 |
| Candidate single versus candidate duplicate | 50 | 105 |
| Chrome single versus Chrome duplicate | 28 | 5 |

The source explains why the implementation can overcount:
`FinishStrokeFill` bypasses structure validation and lifts zero roles to +1;
`SvgPolygonCoverage` sums each loop's unsigned pixel area, then clamps. Summing
partially overlapping areas is not spatial nonzero membership. The existing
disjoint-contour role repair and crossing splitter do not close this problem.

Do not make candidate single/duplicate identity the only browser acceptance test:
the pinned browser itself has a small topology-dependent difference here.
Test mathematical membership independently, then compare each actual input to
its own reference. This is an R34/S11 shared-path problem, not another opacity
patch or a reason to special-case duplicate input strings.

## R41: degenerate gradient binding paints a black stroke

Fresh exact input:

```xml
<svg xmlns="http://www.w3.org/2000/svg" width="16" height="16">
  <defs>
    <linearGradient id="g" x1="0" y1="0" x2="1" y2="0">
      <stop offset="0" stop-color="#f00"/>
      <stop offset="1" stop-color="#00f"/>
    </linearGradient>
  </defs>
  <path d="M2,8 H14" fill="none" stroke="url(#g)" stroke-width="2"/>
</svg>
```

Chrome paints nothing. The renderer returns black pixels in x=2..13, y=7..8:
**24 changed pixels, maximum alpha/channel error 255**. The equivalent `<line>`
spelling explicitly rejects objectBoundingBox gradient strokes; a test of that
spelling alone would miss the accepted path defect. The earlier design record
described a “line” without retaining the failing SVG; its deleted probe generator
established that it was a path. This review recreated and reverified it.

Repair paint binding for zero geometric width/height, distinguish geometry bounds
from stroke extents, and cover linear/radial, horizontal/vertical, local instances
and explicit userSpace controls. Keep a permanent failing-input regression.

## R33: preserve the repair already present

The four polygon rasterizers now map clip boxes through root/output mapping and
multiply by `ClipBoxCoverage`. The old description of bounds-only clipping is
stale. This fresh 8x8 case is **pixel-exact**:

```xml
<svg xmlns="http://www.w3.org/2000/svg" width="8" height="8" viewBox="0 0 16 16">
  <defs><clipPath id="c"><rect width="7" height="16"/></clipPath></defs>
  <polygon points="0,0 16,0 0,16" fill="red" clip-path="url(#c)"/>
</svg>
```

It exercises a mapped half-pixel clip through diagonal geometry. It does not
prove every fractional phase, scale, paint, clip intersection or arbitrary path
clip. Keep this repair while extending shared clipping; do not reopen its original
coordinate-space bug as though the helper had not changed.

## R27: evidence retention and support reporting

`FixtureManifestTests` executes all exact and unsupported entries. That is a real
gate. Known-difference fixtures, however, assert only three aggregate statistics;
research fixtures assert additional bounds/counts but still not complete candidate
identity. Both can miss a changed error layout. Reference hashes do not identify
the candidate, and browser identity fields are not consistently checked against
an allowed historical pin/recipe set.

`docs/RESEARCH_PROBES.md` says to delete exact probes, and `ResearchProbeTests`
requires every renderable research case to be inexact. This loses the controls
needed for safe calibration. Graduate exact original probes into the existing
exact fixture corpus with provenance; never discard an independently useful
success. Preserve incorrect semantic examples too, not just calibration residuals.

The public APIs return PNGs for known-inexact families without per-result fidelity
status. Keep preview limitations explicit. A support-policy/API change needs
deliberate design; this review does not invent a new approximate mode or silently
remove existing experimental rendering. Admission and exactness remain separate
reported facts.

## R30/R35/R37/R38/R39: architecture and resource work remaining

- Four polygon types and four raster loops repeat geometry, mapping, bounds,
  clipping, coverage and ownership, differing mainly in paint. Consolidate that
  path in buildable steps; preserve calibrated rectangle/band fast paths.
- `SvgDevicePoint` often holds pre-root coordinates. Integer `AxisTransform`
  remains the inherited carrier; the general affine kernel is not a public
  transform implementation. Leaf-only parse widening cannot fix container maps.
  Retain verbs/control points until the complete instance/device map is known,
  or prove a conservative bound. Existing magnification rejection gates prevent
  misuse but do not deliver reusable scalable curves.
- `SvgComputedStyle` now carries cascaded stroke values, so the original blanket
  CSS-discard finding is outdated. It still carries strings and separate branches
  repeatedly parse dashes/widths. Consolidate specified/computed/admitted stroke
  state while extending actual inventory blockers, without reopening fixed cases.
- Raster mapping now reserves arrays before allocation and charges vertices times
  evaluated pixels. Definition lifetime repairs and smaller curve scratch exist.
  However, `FinishStrokeFill`/`FinishPolygonFill` allocate retained points, ends
  and roles before `SvgPolygonFill.Create` reserves their scene storage. Fix the
  transfer boundary, including simultaneous old/new buffers during growth.
- Full fan scans remain proportional to bounding-box pixels times vertices.
  Nesting's contour-pair loops also scan contour vertices; pair count alone is
  not the complete operation cost. Shared active-edge/spatial work must account
  setup, intersections, spans and inner scans, with during-phase cancellation.
- Group opacity allocates full output-size surfaces; crop only with correct
  origins, bounds and operation order, and test nested-layer budgets. The current
  benchmark baseline does not establish curve-heavy/wordmark throughput.
- API_CONTRACT still says fractional resolved dimensions reject, despite the
  implemented rounding behavior. SUPPORT_MATRIX contains stale prose counts.
  Synchronize contracts with implementation tests and manifest-derived totals.

The existing typed kernels, budget helpers, oracle tooling and regression corpus
are sufficient to start. A new rendering framework, tool project, native backend
or another broad reference-source survey is not a prerequisite.
